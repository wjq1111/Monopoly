# 《我们的家》测试流程与用例规范

更新日期：2026-09-05

本规范建立“需求来源 → 用例 → 实际执行 → 证据 → 逐例结论”的可追溯流程。旧 M0 套件覆盖本地开局预览，范围标识为 `legacy_m0`；新主场景的联机入口与棋盘使用独立检查，不能沿用 M0 结果声称通过。测试脚本、截图或录像已经生成，不代表对应需求已经验收通过；每项结论必须有同一次运行的实际结果。

玩法依据为[策划规则整理](../故事审阅与开工前条件.md)，实现范围依据为[技术方案与实施计划](../技术方案与实施计划.md)。素材表现另遵循[素材风格与生成规范](../素材风格与生成规范.md)，通用交付遵循[协作规范](../../CONTRIBUTING.md)。本文件不记录某次测试的通过结果，实际结果保存在 `docs/testing/执行记录/`。

## 当前套件范围

[完整 M0 回归入口](../../scripts/self_test.ps1) 使用 `tests/test_catalog.json` 的原用例编号；其 GUI 固定加载 [旧本地预览场景](../../src/app/main.tscn)，不随 `project.godot` 的正式主场景切换。新主场景为 `res://src/app/game_shell.tscn`，联机入口与棋盘按 [board_check.ps1](../../scripts/board_check.ps1) 的独立范围执行，分别记录需求、输入版本、结果和证据。旧报告保留原版本与历史结论，不改写为当前界面通过。

## 尺寸适配与运行稳定性分开检查

主动调整窗口后排版正确，只证明该尺寸的终态适配；不能推导为正常操作时不会跳变。固定窗口稳定性见 TC-BOARD-010：连续观察至少60秒，覆盖入局、29格查看三轮、真实状态更新和面板往返，逐帧记录含边框外窗、内容区、逻辑视口、全局缩放和已建立的棋盘区域。尺寸先变后恢复也应失败，不只比较起点和终点。

`scripts/board_check.ps1` 默认运行功能与稳定性检查；`-StabilityOnly` 仅运行导入及新增稳定性用例。本轮普通功能GUI不主动轮转尺寸，未启用的TC-BOARD-002标NOT_RUN；要检查旧四组尺寸，显式加`-ResolutionSweep`，测试窗口标题说明会主动调整。全屏按钮往返属于明确的显示操作，在稳定性用例中单独记录，不将这些主动变化算成普通操作违规。

自动验收窗口和用户游玩窗口必须可区分；只操作本例窗口和自建服务。采用人为注入短暂尺寸变化验证检测器时，单独记为负向诊断；预期失败能证明检测器可发现该变化，不能作为产品自然故障的证据。用户报告未复现时保持待复现，不能因某配置下一次通过便把报告关闭。

## 测试节奏

以一项可验收需求为单位安排测试，不把每次编辑或每轮工作记录当作完整自测的触发条件。

| 时点 | 应做的检查 |
|---|---|
| 需求开发中 | 按风险做必要的针对性检查，例如语法、单个规则分支或当前界面；不每次改动都跑完整流程 |
| 一项需求完成 | 对照约定行为执行该需求的用例及受影响回归，记录实测与证据；不重复执行无关需求 |
| 阶段验收或跨模块整体验证 | 运行完整自测，并补齐该范围要求的实际视觉、输入或其他专业检查 |
| 仅文档或布局调整 | 检查来源、链接、一致性及受影响的实际布局即可，不触发完整自测 |

针对性检查按已有入口和当前目标选择最小必要范围，不虚构脚本尚不支持的筛选参数。发现失败时修复并复验相关范围；跨模块影响确需整体判断时再执行完整流程。逐轮工作记录继续保留，注明本轮做了哪些检查、哪些未运行以及原因，记录本身不要求重新测试。

## 1. 先固定需求依据

开始编写或更新用例前，先检查工作区状态，读取相关需求和当前实现，区分以下三类依据：

| 类型 | 记录方式 | 如何用于测试 |
|---|---|---|
| 已确认玩法 | 记录需求 ID、来源文件、标题或截图页码、能够独立理解的短摘录 | 从确认规则推导输入和预期结果 |
| 技术要求 | 记录技术来源，并关联它服务的玩法或交付要求 | 验证角色唯一、状态隔离、真实渲染、重复结算防护等技术约束；不称为原故事规则 |
| 待定设计 | 记录问题、来源和受影响需求 | 能编写前置和待决分支，但不能猜一个预期值后记为通过 |

需求 ID 在语义不变时保持稳定，不随文档行号变化重新编号。标题和行号用于定位，短摘录用于确认含义，来源文件 SHA-256 用于确定版本。需求发生实质变化时更新基线与用例版本，保留旧执行记录；拆分或替代需求时记录 ID 之间的关系，旧 ID 不转给另一项需求。

规则来源优先使用已经整理的确认内容。涉及原截图的条件时保留截图页码和文件位置；只有截图但尚未完成辨读的内容不能假装已有可执行断言。用户后续明确确认先同步到需求依据，再进入测试目录。

每次运行保存需求、用例目录、源码、场景及配置的输入清单和哈希，并记录 Godot 版本、Git 提交号及工作区是否有改动。Git 提交号不能单独代表存在未提交改动的工程。输入清单不包含本次生成的日志、截图、录像和执行报告，避免输出改变输入基线。

运行前后核对输入版本。测试途中相关源码、需求或用例发生变化时，本次结果不能用于证明修改后的版本已通过，应保留旧记录，并在对应需求验收时重跑受影响部分；不因此要求开发中的每次修改立即完整自测。

## 2. 从需求建立覆盖矩阵

机器可读的用例目录维护在 `tests/test_catalog.json`。逐例结果必须引用其中存在的用例 ID，并通过用例关联到需求 ID 和来源。不要另建一份编号和状态可能不同步的手工“通过清单”。
目录当前使用 `schema_version = 1`，`scope = legacy_m0` 与 `scene_path = res://src/app/main.tscn` 明确旧回归边界。需求条目使用 `id`、`kind`、可选 `parent_ids` 及 `sources`；每项来源保存 `path`、`section`、`quote`。用例条目使用 `id`、`requirement_ids`、`suite`、`priority`、`preconditions`、`steps`、`expected`、`cleanup` 和 `evidence_required`。`suite` 区分 `domain`、`gui` 和 `manual`。

`domain.json` 与 `gui.json` 记录 `run_id`、`engine` 及逐例 `cases`；GUI 的 `metadata` 另记录 `scope`、实际加载的 `scene_path` 和仅供对照的 `configured_main_scene`；每例通过 `case_id` 关联目录，保存 `status`、`assertions`、`evidence` 和 `reason`。来源哈希和完整输入版本由本次 `manifest.json` 记录。依据类别、实现状态、测试类别等模板内容可以在目录说明、来源文档及报告中表达；未来变更机器结构时同步升级 schema 和校验器，不能写入字段后假定现有程序已经理解。

覆盖矩阵至少能回答：

| 内容 | 必须呈现的信息 |
|---|---|
| 需求 | 稳定 ID、简要内容、确认状态、来源及当前版本 |
| 实现 | 已实现、部分实现或未实现；对应阶段和实际代码入口 |
| 用例 | 用例 ID、检查层次、正向/边界/异常类别、优先级 |
| 执行 | 本次状态、实际观察、失败或未执行原因 |
| 证据 | 对应日志、结构化结果、截图或录像；输入版本是否仍有效 |

M0 至少覆盖角色数量与唯一性、合法选择顺序、初始等级与野性、饱食度 3/5、半点显示、非法输入拒绝、状态副本隔离，以及选满前禁用、建立预览和重新选择的界面流程。相同需求可以同时需要领域用例和 GUI 用例，不能用一个层次的结果替代另一个层次。

未来需求继续保留在矩阵中。例如月份跨年、经验升级、觉醒、濒死送医、最终战、联网和重连目前不能从 M0 测试推导出通过。尚未接入可执行入口的用例标注未实现及 `NOT_RUN`；存在待决规则或必要环境缺失时，按实际原因记录 `BLOCKED`。两种情况都不计入通过数。

本矩阵可以分阶段维护。尚未拆分完的原稿必须注明“待补用例”，不能因为目录已经包含若干未来用例，就声称覆盖了完整故事。

## 3. 每条用例的内容

以下为用例内容模板，机器字段的实际命名以 `tests/test_catalog.json` 为准。示例中的占位符应换成目录中的正式编号。

```text
用例 ID：<稳定用例ID>
标题：<可观察的行为>
需求 ID：<一个或多个需求ID>
依据：<文件、标题/截图页码、短摘录、来源哈希>
依据类型：已确认玩法 / 技术要求 / 待定设计
实现状态：已实现 / 部分实现 / 未实现
阶段与优先级：M0–M5；P0 / P1 / P2
类型：正向 / 边界 / 异常
检查层次：领域 / 场景结构 / 引擎GUI / OS输入 / 导出包 / 多机网络 / 视觉或听感
前提：<初始状态、角色、环境、依赖条件>
数据：<具体输入、确定的骰子序列、需要的物品或网络条件>
步骤：<按顺序列出可重复动作>
预期：<每个关键步骤对应的状态、界面或输出>
自动化入口：<脚本及具体用例入口，尚未实现则明确填写>
证据要求：<必须保存的结果、日志、截图节点或录像区间>
清理条件：<如何解除输入、关闭本次进程、恢复测试状态；保留证据>
```

P0 用于工程无法启动、基本流程不可继续、状态或进度错误等阻断问题；P1 用于主要行为及重要边界；P2 用于对主要流程影响较小的表现和辅助检查。优先级表示执行和修复顺序，不用于隐去未通过项。

步骤写玩家动作或明确的规则输入，预期写可观察结果。不要把“调用某个函数不报错”当作所有预期，也不要读取实现中的同一公式作为唯一答案。例如奶牛伤害的期望值来自已确认的计算顺序，而非先调用待测伤害函数再拿它的返回值断言自身。

执行记录与用例定义分开。用例说明“应该发生什么”，本次记录说明“实际发生了什么”，后者不能预先填入 `PASSED`。

## 4. 按层执行，分别保留证据

| 层次 | 执行内容 | 能证明的范围 |
|---|---|---|
| 导入与领域检查 | Godot 导入资源，运行规则与状态断言 | 脚本可用、数据约束和已覆盖规则输入的结果 |
| 场景结构检查 | 实例化实际场景，检查节点、连接和呈现数据 | 已覆盖的场景装配与状态反映 |
| 实际渲染 GUI | 启动 Godot 4.6.1 图形窗口，使用正常 GUI 输入路由并保存实际渲染图 | 被测窗口尺寸和输入流程下的控件响应、状态和画面 |
| OS 输入与导出包 | 用操作系统鼠标/键盘操作实际运行的程序，并测试导出程序 | 对应设备、窗口焦点和分发形态下的使用情况 |
| 多机与恢复 | 三台设备联机、掉线、重连、保存及恢复 | 被测网络、版本和时序下的联机行为 |
| 视觉与听感 | 实际查看画面、播放动画和试听声音 | 明确记录的显示、节奏、风格和音频表现 |

`scripts/check.ps1` 是可按风险选用的快速检查入口，包含导入、领域和入口检查，不要求每次修改都运行。`scripts/self_test.ps1` 是旧 M0 范围内阶段验收或整体验证的完整回归入口；它复用相同的 Godot 导入及 `run_tests.gd`，然后增加旧场景的实际渲染 GUI 和追踪校验，不再次调用快速脚本本身。新的联机入口和棋盘使用 `scripts/board_check.ps1`，不计入旧 M0 用例通过率。即使快速检查通过，也不能替代图形窗口、操作系统输入、三台机器、正式素材风格或音频试听。

### GUI 输入的执行要求

`tests/run_gui_tests.gd` 固定加载 `res://src/app/main.tscn`，运行在真实 Godot 图形窗口和项目 Compatibility 渲染器中，记录实际显示后端、渲染方式与窗口尺寸。为保持旧用例的尺寸前提，仅在测试进程中将窗口最小限制清零、窗口与内容尺寸设为 1100×760；不改变新主场景的项目显示配置。无法建立图形环境时保留错误和阻塞原因，不切换为无界面图片拼接后声称图形验收通过。

GUI 用例根据当前控件位置构造鼠标移动、按下和释放事件，通过 `Input.parse_input_event` 送入引擎，经过正常 GUI 路由。该 API 可将事件送入 Godot 输入处理；GUI 的接收与传播由控件位置和相关输入设置决定。[Godot Input 文档](https://docs.godotengine.org/en/4.6/classes/class_input.html)、[InputEvent 路由文档](https://docs.godotengine.org/en/4.6/tutorials/inputs/inputevent.html)。

禁止把 `button.pressed.emit()` 或直接调用按钮处理函数记作 GUI 点击验收。它们可以用于明确标注的结构检查，但绕过了控件命中和禁用等输入行为。GUI 检查应等待布局与画面更新，验证操作前后的状态，再从实际渲染结果保存截图。

这里的鼠标动作是**引擎内输入注入**，不等同于操作系统鼠标操作。报告必须写明输入方式。真实 OS 鼠标、焦点切换、桌面缩放及不同设备上的操作需要另设用例，未执行就保留 `NOT_RUN`，不能扩大本轮结论。

### 截图与录像的执行要求

截图应来自本次 Godot 运行中对应检查点的实际渲染帧。每张图关联用例 ID、步骤或检查点和运行 ID。不能将设计稿、其他渲染工具重画的界面或上一次运行的图片作为本次证据。

可选录像通过 `scripts/self_test.ps1 -RecordMovie` 使用 Godot `--write-movie` 输出 AVI，记录引擎渲染的过程。Movie Maker 支持固定帧步进，生成视频不证明操作系统桌面过程或真实耗时；它也不替代性能测试。录制是否成功、文件是否可读、哪些过程已查看应分别记录。[Godot Movie Maker 文档](https://docs.godotengine.org/en/4.6/tutorials/animation/creating_movies.html)。

不需要录像的运行仍可凭相应的结构化结果和必要截图验收；未启用录像就记为未录制。若某条用例明确需要连续过程证据，而本次只有末帧截图，则该用例的证据尚不完整。生成文件只表示采集完成，未查看的画面和未试听的声音继续注明未检查。

## 5. 当前执行入口与操作顺序

需要旧 M0 阶段验收或其范围内整体验证时，在项目根目录打开 PowerShell。M0 完整回归由 `scripts/self_test.ps1` 编排，支持 `-GodotPath`、可选 `-PythonPath`、可选 `-RecordMovie` 和 `-WindowPosition`；窗口位置默认为 `80,80`。Python 标准库仅负责编排、报告与追踪校验；规则和 GUI 仍由真实 Godot GDScript 执行。命令写入文档不能作为其运行成功的证据。

```powershell
# 按风险和目标需要选用快速检查
powershell -ExecutionPolicy Bypass -File .\scripts\check.ps1

# 旧 M0 阶段验收或其范围内整体验证：完整回归
powershell -ExecutionPolicy Bypass -File .\scripts\self_test.ps1

# 新联机入口与棋盘：独立检查，不复用旧 M0 通过结论
powershell -ExecutionPolicy Bypass -File .\scripts\board_check.ps1

# 同一次旧 M0 流程额外保留Godot录像
powershell -ExecutionPolicy Bypass -File .\scripts\self_test.ps1 -RecordMovie

# 需要指定引擎时
powershell -ExecutionPolicy Bypass -File .\scripts\self_test.ps1 -GodotPath 'E:\MyGames\Godot_v4.6.1-stable_win64.exe'
```

`self_test.ps1` 的退出码含义：

| 退出码 | 含义 |
|---|---|
| `0` | 当前 legacy_m0 必测项目全部验收通过；不代表新主场景、联机、棋盘或完整游戏验收 |
| `1` | 执行、追踪校验或用例失败/阻塞，按报告定位具体原因 |
| `2` | 自动用例通过，人工视觉仍为 `NOT_RUN`，本轮 M0 验收尚未完成 |

自动运行结束后出现 `2` 是明确的待审阅状态，不能当作 `0`。`review_test.ps1` 在实际审阅并完成当前 M0 验收后返回 `0`，失败、阻塞或记录校验失败返回 `1`。

决定执行旧 M0 完整回归后的顺序：

1. 读取需求与用例目录，校验来源、短摘录、需求 ID 和用例 ID；保存本次输入版本。
2. 创建唯一运行 ID 和独立输出目录，记录环境与命令，避免覆盖既有失败证据。
3. 先运行测试编排器的 12 项结构校验测试，检查缺失来源、未知编号、失败断言及证据缺失等拒绝行为；这些是测试工具自检，不计作游戏需求用例。通过后执行 Godot 导入，再运行 `tests/run_tests.gd` 产生逐例结构化结果；与快速入口共用已有 Godot 检查。
4. 在图形环境运行 `tests/run_gui_tests.gd`，执行正常 GUI 输入流程并保存截图；按参数额外录制录像。
5. 校验结果 ID、状态、数量与证据引用，补齐未执行项和阻塞原因；核对运行结束时输入仍是同一版本。
6. 保存机器结果与输入清单，生成中文执行记录；实际查看相应用例要求的画面或录像，单独记录表现检查结果。
7. 对失败建立复现记录，修复后新建一次运行，链接旧失败和新回归结果。

导入失败、图形窗口失败、超时或脚本崩溃时，不要求依赖该前提的用例继续运行。尽量保留已完成结果和失败日志，其余逐例注明未执行原因；不能只显示之前某一步的“通过”而省略后续中断。相关失败必须影响整次运行结论及检查入口退出码。

OS 鼠标、导出包、局域网三机、重连、跨年月份与战斗等按对应阶段另行验收。本入口未实际执行的内容不能写成已测。

## 6. 证据存放与一致性

每次运行的本地证据保存在：

```text
.artifacts/self-tests/<run-id>/
  baseline/                 需求、用例与源文件原始副本
  harness.log               测试编排器结构校验结果
  import.log                资源导入日志
  domain.log                领域执行日志
  gui.log                   图形窗口执行日志
  *.engine.log              对应Godot日志
  domain.json               领域用例结果
  gui.json                  实际渲染GUI用例结果
  input_events.json         引擎内输入记录
  screenshots/              Godot截图
  gui.avi                   启用录制时的录像
  manifest.json             输入清单与哈希
  summary.json              汇总与追踪校验结果

docs/testing/执行记录/<run-id>.md
```

具体文件以本次执行记录中的证据引用为准。执行记录应包含运行 ID、时间、版本、环境、命令、逐例状态、实际观察、证据链接、覆盖数量、阻塞事项和下一步。报告保存为可追踪文档，本地大体积证据不自动上传；用户要求分享或发布时按已授权范围处理。

证据引用必须指向实际存在的文件。源码哈希证明被测版本，结果 JSON 证明具体断言和状态，截图证明对应时刻的画面，录像补充连续过程；它们各有作用。不能用一张通用启动截图证明全部用例。

人工视觉用例 `TC-VIS-001` 默认保留 `NOT_RUN`。必须实际查看本轮截图及该用例要求的其他证据后，才通过 `scripts/review_test.ps1` 写入 `visual_review.json`，记录逐项观察及其引用；具体命令见下一段。不能因自动 GUI 结果为通过就自动填写人工视觉通过，也不能只勾选状态而没有本轮查看依据。

实际打开本轮用例要求的初始、部分选择、完整预览、清空重选和再次预览截图后，才执行以下审阅命令模板。替换运行 ID、审阅者和结论文字；`-Evidence` 是以逗号分隔的一个字符串，使用相对本次证据目录的路径。若没有实际查看，保留 `NOT_RUN`，不调用审阅命令补成通过。

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\review_test.ps1 -RunId '<本次RUN_ID>' -Status PASSED -Reviewer '<实际审阅者>' -Notes '<实际观察、范围和结论>' -Evidence 'screenshots/01_initial.png,screenshots/02_partial.png,screenshots/03_selected.png,screenshots/05_reset.png,screenshots/06_reselected.png'
```

`-Status` 接受 `PASSED`、`FAILED`、`BLOCKED`；发现显示问题或无法完成所需检查时填写对应状态和原因。需要指定 Python 时追加 `-PythonPath '<python.exe的实际路径>'`。审阅脚本核对运行、来源版本和证据引用，记录审阅者提供的结论；程序不会自动识别图片内容或证明审阅者已经看过图片。

一致性检查至少拒绝：未知或重复的需求/用例 ID、缺少来源、短摘录与来源不符、来源版本不一致、结果对应不到目录、执行结果缺项且无说明，以及已通过用例缺少其要求的证据。自动化尚未实现的校验明确记录未覆盖，不伪称已具备。

执行报告可长期保存，但指向 `.artifacts/` 的链接仍是本地证据。移动或清理证据时保留原报告，注明证据已迁移或不可用；不能让失效链接继续表现为当前可核验材料。

## 7. 逐例状态与通过条件

| 状态 | 使用条件 |
|---|---|
| `PASSED` | 实际执行了本例规定的步骤和断言，预期满足，所需证据有效 |
| `FAILED` | 实际结果偏离预期，或本应执行的检查、结果与必要证据出现错误 |
| `BLOCKED` | 已知前提、需求裁定或环境阻塞了执行，必须写出具体阻塞点 |
| `NOT_RUN` | 本轮未执行，或尚未实现相应可执行入口；必须写明原因 |

实现状态和执行状态是两列。未实现需求不会因为没有失败结果变成通过；技术实现存在也不会自动变成已验收。图像已经保存与实际查看通过同样分开记录。

每次报告列出目录总数、各状态数量、当前阶段必测数量，以及其他阶段未执行数量。可以给出 M0 范围内的执行率和通过率，但必须明确分母；不能把未实现、受阻或未运行用例从全项目矩阵中删除，再称“全部通过”。断言条数也不能当作用例条数或需求覆盖数。

“M0 验收通过”要求本轮 `legacy_m0` 必测用例和证据检查均满足，没有未处理的失败、阻塞或漏测；本结论只适用于旧本地预览场景，不能用于新的 `game_shell.tscn`。总体游戏验收仍需后续章节、联机、存档、素材及实际设备流程。若本轮只有部分层次通过，报告具体层次，例如“领域检查通过，图形环境受阻”，不要给出全阶段通过。

## 8. 随机规则、分支与回归

后续游戏包含不可预知行动和骰点，用例按已确认规则构造可复现输入：

- 有限骰面覆盖所有合法结果及适用的非法输入；多骰、改点、连投与重投同时覆盖已确认的组合和结算先后，长序列与更大组合明确采用的覆盖策略，不声称穷举无限序列。
- 数值门槛分别检查低于、等于、高于，以及一次变化跨过门槛。终战阈值不能只测刚好扣到对应数值。
- 主线检查正常顺序、提前到访、超等级到访、材料先取得、不同猫先到达和主线/个人事件条件重合。
- 重复点击、重发命令、多人同时请求、恢复旧状态及重试检查幂等性，同一次奖励、扣除、觉醒或复活只结算一次。
- 受伤、濒死、挂靠、强制移动、觉醒排程和当前行动的组合，先补齐策划裁定，再写明确预期。
- 三人联机区分同机三进程、局域网三台设备和互联网连接；重连、主机退出及存档恢复按实际实现和约定范围验证。

固定骰子序列是测试输入，不能借此改变正式对局的随机机制或擅自禁用原有控点技能。使用随机种子时记录工具和实现实际支持的参数；保存具体失败输入，避免仅凭种子假定跨版本可重现。

失败记录包含用例 ID、输入基线、复现步骤、预期、实际、日志、截图或录像，以及影响范围。先保留失败，再修复；回归创建新运行 ID，验证原失败和受影响的相邻规则。旧失败状态不被新结果覆盖，不通过反复运行挑选一次成功来隐去间歇性问题。

需求、源码、配置、素材或测试入口变更后，先判断影响到哪些用例，开发中只做必要的针对性检查。受影响的旧结论对当前版本标为过期或待重验，历史运行仍保留当时状态；在对应需求完成时固定新基线、执行该需求与受影响回归，不因每次修改立即完整重跑。无关部分可保留既有有效证据，但需说明版本和影响判断；仅文档或布局调整按来源、链接、一致性及布局检查收尾。
