## 1. 来源与状态约定

需求来源优先级：用户最新明确确认 → [策划规则整理](../故事审阅与开工前条件.md) → 对应原稿截图。用户新裁定应同步回策划，再改需求和用例；遇到冲突不能让测试选择自己喜欢的数值。

- “策划·二”等简写指策划文档对应编号章节，后接真实小节名称。
- “技术”指 [技术方案与实施计划](../技术方案与实施计划.md)；技术派生需求采用 `TECH-` 编号，不能冒充原故事。
- “风格”指 [素材风格与生成规范](../素材风格与生成规范.md)。
- 原稿页码指 [故事截图目录](../主线剧情故事截图)，地块编号依据 [原棋盘图](../主线剧情故事截图/棋盘大致样子.png)。原截图使用的旧生存术语和冲突数值以当前策划为准。
- M0 自动及界面用例见 [M0 测试用例](M0测试用例.md)；未来玩法详细用例见 [策划测试用例](策划测试用例.md)。

三种状态独立维护：

| 列 | 可用状态与含义 |
|---|---|
| 实现 | 未实现 / 部分实现（必须写范围）/ 已实现；规范建立、候选图生成属于制作进展，不等于游戏行为已实现 |
| 设计 | 已编写（有前提、操作与可判断预期）/ 部分编写 / 待细化 / 规则待定（无法确定预期） |
| 执行 | 未运行 / 通过 / 失败 / 阻塞 / 不适用；通过、失败必须关联具体运行批次及证据，阻塞必须写原因 |

本表初始执行列对未实现功能统一记“未运行（未实现）”，对确定不了预期的分支记“阻塞（规则待定）”。历史 M0 曾运行的断言记录保留在技术文档；没有逐例证据映射前，不把历史总数直接转成新版每例通过。本轮或后续运行结果以相应测试报告为准，不在此伪造结果。

## 7. 覆盖闭环

每次开发先选本表需求，再编写/更新用例，然后实现和真实运行，最后记录每个测试点结果。变更需求时列受影响用例；变更实现不允许暗改用例预期来消掉失败。

通过率只能按本次实际执行的明确用例计算，并同时报告总登记数、已设计数、未实现数、规则阻塞数、未运行数、通过数和失败数。参数化用例的每组输入单独保留结果，不用一个通过隐藏其中失败。没有拆完的 29 格和原稿分支必须继续显示为覆盖缺口；本地、无界面、真实窗口、三进程、局域网、导出验收分开统计。
