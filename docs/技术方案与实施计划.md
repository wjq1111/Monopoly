# 《我们的家》技术方案与实施计划

更新日期：2026-09-05

当前已完成 M0、九页布局，以及 **Godot 棋盘与本地 ENet 接口首版**。本轮按用户要求先接入联机选角、常驻棋盘、复用面板和单猫调试，提前验证 M2 的连接与共享状态部分；M1–M5 的规则、故事和完整验收继续保留。详细交付与未做范围见[棋盘首版](ui/Godot棋盘首版.md)。

玩法依据为 [《我们的家》策划规则整理](./故事审阅与开工前条件.md)；原故事截图继续保留在 `docs/主线剧情故事截图/`。技术实现不新增人物、剧情、资源消耗或胜负规则。策划未明确的裁定列入对应阶段的待确认事项。

## 1. 技术选择与实施原则

| 项目 | 选择 | 原因与范围 |
|---|---|---|
| 引擎 | Godot `4.6.1.stable.official.14d19694e` | 本机已验证可用，开发与检查使用同一版本 |
| 语言 | 带类型声明的 GDScript | 降低脚本类型错误，直接使用 Godot 场景和资源 |
| 表现 | 2D，Compatibility 渲染器 | 先满足棋盘、剧情和操作界面所需能力 |
| 首个平台 | Windows | 先完成开发机可运行与三台客户端验证，再决定其他平台 |
| 联机方案 | Godot 高层多人 API、ENet、服务器权威 | 本轮以独立无头服务承载唯一写入端；玩家用客户端连接，不增加第四名主持人 |
| 规则配置 | Godot Resource 与 `.tres` | 将可调整数值与场景显示分开 |
| 规则状态 | 独立于场景节点的状态对象 | 便于无界面检查，后续由主机维护并同步 |
| 饱食度存储 | 以 0.5 为一单位的整数 | 支持原稿的 0.5、1.5，不依赖浮点数判定归零 |

饱食度初始 3、上限 5，在内部保存为 6、10；显示时换回策划中的数值。扣 1 对应内部扣 2。内部单位是实现细节，玩家界面始终使用“饱食度”。若以后原稿出现不同精度，再统一调整单位及存档版本。

系统自动主持意味着规则、随机数和剧情推进由程序执行。服务器权威意味着本局只有一处状态写入权，并不增加一个玩家身份。原计划由玩家房主进程承载；依据本轮本地服务器要求，改为可由同一电脑启动的独立无头服务，便于单猫和正式三人复用接口。这是助手工程选择，正式部署尚未裁定。以后普通骰子的基础随机结果由服务器产生；三花重投、奶牛改点、布偶选点或传送等技能，仍接收玩家合法选择并按原文结算。

Godot 的 [高层多人网络文档](https://docs.godotengine.org/en/4.6/tutorials/networking/high_level_multiplayer.html) 提供 ENet、RPC 和网络权威的实现依据；[命令行文档](https://docs.godotengine.org/en/4.6/tutorials/editor/command_line_tutorial.html) 提供编辑器导入、无界面运行与脚本检查的依据。后续具体 API 写法以该版本文档和本机验证为准。

## 1.1 制作职责：策划、程序、美术、界面与声音

项目职责覆盖完整的 2D 游戏制作。下面是后续工作范围，不代表这些素材或功能已经完成。当前已有规则初始化、房间与棋盘接口、三猫Q版候选和4幅地块样张；尚未确定正式美术风格，也没有正式音频资源。

| 职责 | 负责的工作与交付物 | 如何确认完成 |
|---|---|---|
| 策划与叙事 | 整理原故事、规则、对白、剧情触发条件和素材需求 | 符合已确认原稿，待定问题可追溯，不擅自增加人物关系和玩法 |
| 程序 | 规则、联机、存档、场景装配与资源接入 | 对应阶段的自动检查及真实运行通过 |
| 美术 | 三只猫的造型与表情、棋盘地块、场景、物品图标、剧情插图 | 三猫特征前后一致，尺寸、透明边缘、视角和层级适合游戏内使用 |
| 界面与交互（UI） | 选角、棋盘信息、饱食度与野性展示、仓库、战斗操作、剧情对话、房间与设置界面 | 在 Godot 内可操作，中文清晰，选中、禁用、等待与错误状态可区分，窗口变化不遮挡内容 |
| 动画与特效 | 骰子、移动、受击、技能、场景与剧情转场 | 信息表达清楚，能在实际场景中播放；跳过或重播不会改变规则结算 |
| 音频 | 操作音、骰子与行动音效、环境声、场景配乐，以及需要时的配音；完成剪辑、循环、音量和触发接入 | 实际试听音量、循环和切换，检查静音控制及重复播放；尚未试听时只能报告文件或接入检查 |
| 综合验收 | 把画面、输入、声音、故事和规则放在同一段可玩流程中检查 | 玩家能理解当前情境、轮到谁和可做什么；素材不会遮挡信息或让等待状态含糊 |

美术可以使用图像生成能力制作候选图，再完成符合项目要求的整理与接入；界面需要在 Godot 内实现，静态效果图只是参考。简单音效可以通过程序合成，也可以编辑和接入已有音频。配乐可以先完成情绪、节奏与段落设计；当前尚无可调用的专用音乐或配音生成工具，高质量成品音乐、自然环境录音和配音需结合届时可用的工具或有明确来源的素材，不能把文字方案当作声音文件交付。

每项素材记录用途、对应原稿、尺寸或时长、来源及可用范围、工程内路径和当前状态。状态区分占位、候选、已接入、已验收；未生成或尚未试听的内容如实保留。具体文件清单在开始对应内容时建立，避免先建一批没有内容的目录。

## 1.2 界面布局、组件和素材的制作顺序

布局方案已完成，当前已提取共用Theme与控件并接入Godot；后续继续按实际容器尺寸制作剩余底图与分镜。每次素材制作仍遵循[素材风格与生成规范](素材风格与生成规范.md)，使用同版本基准并完成实际显示检查。正式画风与声音方向仍待样例确定，当前开发界面的配色不自动成为正式基准。

1. **各界面布局图。** 按已确认的“同局连接 → 选角 → 棋盘 → 共同剧情”流程列出需要的界面及状态，先确定信息区域、操作位置、文字容量和图片区域。具体布局见[界面布局与制作顺序](ui/界面布局与制作顺序.md)，交互草图见[布局样例](ui/layout_v001.html)。样例中的未决交互明确标为提案。
2. **共用 UI 组件。** 根据布局确定基准尺寸、字号层级、间距和状态，再制作共用 Godot Theme、按钮、角色卡、数值区、剧情分格及文本容器。可点击操作与动态文字由真实控件承担，组件尺寸和伸缩规则供底图制作使用。
3. **界面底图与剧情画面。** 依据已确定的组件位置、图片区域、裁切方式和留白制作。界面底图不烘焙可变饱食度、野性或按钮文字；剧情画面按照原稿拆分为漫画式画格，与文字分别管理。角色固定特征与正式风格仍按确认的基准执行。
4. **Godot 接入。** 把组件、底图和实际状态装配到相应场景，再验证中文排版、控件命中、选中/禁用/等待反馈和目标尺寸。原型里演示的三人进度或点击看完，只有在交互规则确认并接入真实网络后，才能作为联机功能验收。

M1 起按功能阶段继续扩充已需要的角色、棋盘、剧情及声音资源；M5 负责整体完善和验收。音效与声音样例可以与对应功能并行准备，未试听时保留未验收状态。图像生成完成不等于 Godot 接入，布局原型也不等于游戏已经可玩。

## 1.3 已确认的产品流程与共同剧情

正式产品流程为：**三名玩家连接同一局 → 分别选三花、布偶、奶牛 → 进入大富翁棋盘 → 任一角色触发剧情时三人共同观看并看完 → 返回对应游戏流程。** 系统自动主持；创建服务器的玩家也可作为三名玩家之一进入，不增加主持席位。

共同观看覆盖原稿全部剧情，包括个人事件和个人觉醒。呈现要求是类似四格漫画的分格画面配合文字。个人事件的角色条件、技能、奖励、行动消耗与强制移动按策划分别处理；观看者是全体，不改变规则上的参与者或收益归属。

技术上为同一次剧情保留共享事件标识、内容版本和触发角色，向三端呈现相同事件；规则结算与文本、画面播放分开，防止多人观看导致重复奖励。每段画格和文字保留对应原稿来源，表现层不新增故事。

“如何判定三人都看完”“是否逐页同步”“是否允许跳过”“阅读时掉线如何处理”尚未裁定。共享进度展示、每人点击“看完了”等已作为显式调试预览接入，正式规则仍属交互提案；不预设超时跳过、主机代确认或逐页一致。M2 先验证同一事件能向三端共同呈现，完整的阅读结束衔接须按确认结果实现。

下列保留原脚手架范围。当前运行入口为 `src/app/game_shell.tscn`；新增 `src/ui/` 共用组件、`src/network/` 服务器与客户端、`assets/art/` 候选素材、`scripts/board_check.ps1` 新需求验收。原 `main.tscn` 保留给旧 M0 回归。

以上目录描述原M0脚手架。当前实际新增模块见本节开头；战斗、存档等未实现模块仍不预建空壳。

- `game_rules.gd` 声明规则资源及有效性约束；`default_rules.tres` 保存默认数值。界面不再复制另一份等级、饱食度或经验配置。

- `main.gd` 负责装配和显示，不直接实现月份扣除、经验升级、伤害或剧情奖励。
- M0 提供本地顺序选择：依次选定三名角色，顺序由操作者决定；点击“建立本地预览”后生成并显示三猫初始状态。玩家可使用任意合法顺序；这只验证本地初始化，联机身份、选角确认与顺序锁定现已在棋盘首版接入，正式三台设备验收仍在M2。
- `run_tests.gd` 校验领域状态，不依赖玩家点击界面。检查失败必须返回非零退出码。
- `godot.ps1` 集中处理开发机引擎位置；项目文件不绑定个人机器的绝对引擎路径。`check.ps1` 作为本地和后续自动化共用入口。

## 3. 开发入口

以下命令在项目根目录执行。启动脚本不带引擎参数时直接运行游戏；带 `--editor` 时打开工程编辑器。

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\godot.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\godot.ps1 -GodotArgs '--editor'
powershell -ExecutionPolicy Bypass -File .\scripts\check.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\board_check.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\self_test.ps1 -RecordMovie
```

Godot 启动与检查脚本均支持 `-GodotPath` 指定引擎文件；依次查找环境变量 `GODOT_BIN`、项目上一级目录中的 Godot 4.6.1 引擎、PATH 中的 `godot`。首次运行缺少脚本类缓存时会先执行无界面导入。优先通过这一入口启动和检查，避免编辑器与命令行混用不同 Godot 版本。实际执行结果记录在本次交付说明中，不将上述命令的存在当作检查通过。

## 4. 按什么顺序做

### M0：项目脚手架——本轮交付范围

实施顺序：

1. 建立 Godot 工程，名称为《我们的家》，指定 2D Compatibility 和启动场景。
2. 建立规则 Resource、默认配置及配置有效性检查。
3. 建立初始会话：三只猫均为 1 级、当前经验 0、饱食度 3/5，并保留给定角色顺序。
4. 制作可启动的开发入口，直观显示当前规则和三猫状态。
5. 提供 Windows 启动脚本与统一检查脚本。
6. 写入开发、文档和提交规范；执行导入及状态检查。

验收标准：

- 指定版本 Godot 可以导入工程并启动主场景，无脚本解析错误。
- 三猫名称与初始状态正确；更换合法顺序会保留该顺序，不重新按角色名称排序。
- 重复角色、缺少角色和无效规则不能建立看似有效的会话。
- 自动检查覆盖初始化、顺序保留和非法输入，失败会使检查命令失败。
- 界面不会把“下一月”“开始战斗”“联机”显示成已经可玩的功能。
- 没有将原始剧情截图改写成运行时规则，也没有提前固化尚未确认的裁定。

首次脚手架交付的历史验证记录（2026-09-05；下列 37 项是当时断言数）：

- Godot 4.6.1 无界面导入、37 项行为断言和主场景启动检查通过。
- 使用不含 `.godot/` 缓存、且目录名带空格的独立工程副本验证了启动脚本：首次自动导入后可以启动。
- 已使用 Compatibility 渲染器检查未选角和完成选角两种界面；中文、三猫顺序、等级及饱食度显示正常。
- 工程代码已提交为 `b843af3` 并推送至 [wjq1111/Monopoly](https://github.com/wjq1111/Monopoly) 的 `main` 分支，保留远程初始化提交。缓存和检查产物被忽略，脚本 `.gd.uid` 保留。
- 中文项目技能和 Git 提交技能均已完成元数据、相对链接与编码检查，并通过官方 `quick_validate.py`。验证所需 PyYAML 安装在被忽略的 `.artifacts/skill-validation/` 下，不随项目提交。

脚手架已交付。后续新增的需求驱动自测包含 8 条领域用例、5 条引擎 GUI 用例和 1 条人工视觉用例，取代以断言总数代替逐例追踪的做法；实际结论见[执行记录](testing/执行记录/)，不覆盖上述历史结果。M0 GUI 固定使用原main.tscn场景、真实Godot渲染和正常输入路由，人工视觉需实际查看本轮截图再记录。M0 验收不等于完整游戏或三人联机验收。

### 界面规划阶段：布局先行（布局已交付）

先做各界面布局，再做 UI 组件、界面底图和 Godot 接入。此阶段安排在已交付的 M0 之后，为 M1–M5 提供共用界面规格；不改变后续功能阶段的范围，也不把原型演示算作联网实现。

该阶段已交付界面清单、布局图和可查看的流程样例，检查“连接同一局后选角”“选角后进入棋盘”“全部剧情三人共同观看”是否在布局中清楚可见。原型里具体的阅读进度和完成按钮标为待确认交互，图片使用占位时保持状态明确。

布局确定后再提取共用 Theme 与组件的尺寸和状态，按这些尺寸制作底图与漫画画格，最后逐个接入实际场景。接入按相应功能进度验收：仅有底图不能通过交互验收，仅有本地演示不能通过三端共同观看验收。

### 棋盘与本地联机首版（本轮）

用户要求先做常驻棋盘界面、分辨率适配、本地服务器与单猫调试，因此将连接和表现部分提前。已实现入口→连接→选角/准备→棋盘，以及地块详情、三猫候选棋子、仓库/角色/设置弹层、原稿四格接口预览。服务端校验玩家身份、准备状态、命令顺序与版本，调试移动只在显式单猫模式可用。

初始状态继续引用默认规则；仅位置调试，不补定普通步行路线。漫画确认等待是演示接口，正式条件、奖励与月耗尚未接入。独立无头服务采用UDP 27840，GUI本机按钮只绑定127.0.0.1，独立启动器可供局域网连接，详细范围见[服务器说明](本地服务器与联机接口.md)。

验收针对TC-BOARD-001～009分别记录；29幅插图仅完成4张候选、正式分镜仍占位，这些缺口不因接口测试通过而关闭。最新结果见[执行记录](testing/执行记录/棋盘与本地联机_v001.md)。

### M1：最小本地规则循环

先做一条能够推进状态的短流程，为联网准备稳定接口；完整地块和剧情留到后续。

实施顺序：

1. 将玩家操作统一为命令，建立动作上下文、处理结果与错误反馈；界面不能直接改会话字段。
2. 实现上旬三猫行动、中旬三猫行动、下旬补给、进入新月的阶段转换。
3. 实现月份和季节变化；基础月耗按春 1、夏 2、秋冬 3，只结算一次。
4. 接入棋盘格编号与移动结果，区分普通落点、经过和强制移动，避免隐式触发所有经过格。
5. 实现经验累计、逐级升级及觉醒待处理标记。只建立觉醒的排程入口，完整故事和技能由 M3 接入。
6. 建立少量来源明确的事件，验证前置条件、一次性标记、奖励和当前行动结束之间的关系。
7. 并行制作三猫、棋盘局部与界面样例，在同一段流程中接入基础操作反馈；整理音乐、音效和环境声需求，先验证少量音效。正式美术与声音方向未确定时保留占位。

验收标准：

- 能连续推进跨年月份；同一行动重复提交不会再发奖励或多推进一次时间。
- 1 级获得 25 野性后为 2 级 15/20；继续获得 5 后为 3 级 0/30。
- 未觉醒时不会直接升 5 级，待处理的觉醒不会因跨月丢失。
- 月份与阶段只在当前必须完成的操作结束后推进。
- 移动、经验、月耗及事件结算均可通过无界面场景验证。
- 本地界面能显示月份、行动归属和可操作状态；样例素材及声音的候选、接入和验收状态有明确记录。

依赖裁定：下旬共享补给的操作归属和结束条件、行动暂停状态与阶段衔接，以及本阶段实际接入地块的未决动作细则。先完成无争议的状态转换；需要裁定的分支不写入默认玩法。

### M2：尽早验证三人联机

本轮已提前完成真实本地服务与共享房间接口；M1规则完成后继续通过现有接口传递，并补三独立客户端进程、三设备与正常剧情验证。不要把同机多个peer的协议检查当成完整M2完成。

实施顺序：

1. 实现三名玩家先连接同一局、再各自选择角色，随后进入同一大富翁棋盘；房间、选角和棋盘沿用已经确定的布局与共用组件。
2. 为本局玩家建立稳定身份，将当前网络连接映射到玩家；三猫不重选、不重复占用，开局后锁定角色顺序。
3. 将 M1 命令送到服务器，由服务器校验身份、行动归属、条件和参数。
4. 服务器产生普通随机结果，执行规则并发送带版本的状态更新；界面播放收到的结果。
5. 实现重复命令识别、过期状态拒绝或刷新、非法玩家操作拒绝。
6. 接入玩家连接和离开事件，显示缺席状态。掉线后规则是否继续等待、代行或中止，按用户裁定实现；不可让缺席玩家悄悄丢失行动。
7. 同步完善房间、选角、准备、等待和连接错误的界面；声音只作为提示补充，关键状态同时有文字或视觉表达。
8. 验证任一猫触发同一原稿剧情时三端共同呈现，包含个人事件；阅读完成、逐页同步与掉线衔接按后续确认结果实现。

验收标准：

- 三个独立游戏进程先连入同一局，各自选角后进入棋盘，显示一致的角色顺序、行动阶段、位置与饱食度。
- 任一猫触发的剧情向三端共同呈现，个人剧情不只发送给触发者；观看范围不会让个人奖励变成全员奖励。
- 非当前玩家、错误角色、重复请求和过期选择不能改变规则状态。
- 同一次掷骰或奖励在三端得到相同结果，服务器只结算一次。
- 两端同时请求同一共享事件时，只有一个有效结算。
- 断开一名客户端时，其他端显示明确状态，不继续展示该玩家已成功操作。
- 先在同机多进程测试，再在局域网三端验证；互联网地址、端口可达性与分发方式单独验证，不能用本机连通代替互联网联机验收。

M2 只验证连接和共享状态。进程退出后的恢复、正式重连和存档一致性在 M4 完成。首版不承诺房主迁移。

### M3：章节、战斗、技能与救援

依照原故事逐段接入，每段同时补齐对应事件数据和检查案例。

实施顺序：

1. 按首次外出、寻母、失去住所、寻找新家、鼠王情报、筑巢的前后依赖接入主线。
2. 实现幸福小区主线优先、个人事件留待之后到访，保留原有角色条件。
3. 确认敌方行动与闪避时点后，实现战斗状态、猫的固定顺序、敌方动作和离场处理。
4. 接入逃跑、受伤、濒死、挂靠及 20 号医院，打通部分濒死与全员濒死两条流程。
5. 按等级接入技能及二选一分支，分别验证三花连投、奶牛改点与布偶移动能力。
6. 接入达到 4 级后下一个行动自动到对应格觉醒。
7. 接入最终战解锁、选择进入、全队集合、阈值剧情、失败救场与成功结局。
8. 每接入一段故事，同步补齐对应场景、表情、战斗和共同剧情界面、动画及音效；主线与个人剧情均按漫画式分格画面配合文字制作，三名玩家共同观看。配乐按已经具备的资源接入，不把未取得的音频写成完成。

验收标准：

- 不依赖固定骰点或固定到访顺序，提前练级和乱序到访仍能继续主线。
- 三花连投 2、5 的合计为 7；伤害再乘等级。
- 5 级且已觉醒、选择改点分支的奶牛掷出 1、2，伤害为 `(4 + 5 + 3) × 5 = 60`。
- 鹅、狗召集时按确认规则强制移动；逃跑基础扣 1 且必定成功，其他状态组合按补齐的裁定结算。
- 有可行动同伴时能完成挂靠送医；全员濒死不会等待无人能够执行的送医操作。
- 同一猫的觉醒、同一次筑巢和同一次终战失败救场均只结算一次。
- 主线、个人事件及觉醒均可在三端共同观看并按已确认方式完成阅读；原稿角色条件、行动消耗、棋盘位置和奖励归属保持正确。
- 最终战允许多次失败、多次救场；不同重试继续增加原稿规定的帮助。
- 伤害跨过剧情阈值能够识别，不要求刚好命中那个数值。

### M4：存档、重连与完整故事验证

实施顺序：

1. 为状态和保存格式建立版本号，明确哪些状态可以保存，以及存档失败后的提示。
2. 保存玩家身份与角色顺序、月份阶段、当前行动、角色状态、仓库、任务标记、待处理觉醒及战斗状态。
3. 接入重连身份校验和完整状态同步；网络连接编号不作为永久玩家身份。
4. 恢复待处理选择和结算记录，防止重连后重复领奖、再次月耗或再次复活；同步检查界面恢复和声音重播，避免重连时把所有历史事件再次播放。
5. 整理完整 29 格、季节事件、小游戏、物品和人物剧情，逐条对应原稿来源。
6. 进行三人从开始到结局的连贯验收，并补做跨年练级、乱序探索和终战重试。

验收标准：

- 在动作边界保存并恢复后，状态与保存前一致。
- 若支持处理中保存，其当前选择和结算进度也能精确恢复；没有做到时必须限制保存时点并明确显示。
- 普通客户端重连后恢复原角色和顺序，不新增第四只猫、不重发一次性收益。
- 主机重开并载入存档的流程可验证；它与实时房主迁移是不同能力。
- 原稿事件有实现、来源和验证记录，未明确的条件没有藏在代码里充当默认答案。

### M5：素材完善、体验打磨与导出

进入本阶段前，应已在前面的阶段逐步接入美术、界面和声音；本阶段集中解决完整流程中的缺项和质量差异。

实施顺序：

1. 补齐并统一棋盘、三猫、场景、道具和剧情插图，逐项替换仍留在正式流程中的占位资源。
2. 完善骰子、移动、战斗和剧情呈现，同时保持状态结算不依赖动画时长。
3. 检查三端共同剧情、当前行动、等待同伴和错误提示，使玩家知道下一步能做什么。
4. 完善音乐、音效与环境声的衔接、音量和静音控制；若纳入配音，同步检查字幕与播放时机。配音是否采用仍是制作选择，不默认承诺全量配音。
5. 验证不同窗口尺寸、中文字体、键鼠操作和声音设置；在实际播放中检查音量突变、循环接缝和重复触发。
6. 配置 Windows 导出模板，打包可分发版本，使用导出后的程序再次进行三人联机与完整流程检查。

验收标准：导出程序可独立启动、三端可连接、完整故事可通关、存档重连可恢复；图像、字体与音频依赖完整，窗口变化不遮挡操作，声音设置有效；动画跳过或帧率变化不会导致重复结算。互联网分发与连接方式以实际验证结果说明。

## 5. 状态与网络的边界

后续命令按以下顺序处理：

```text
玩家选择 → 客户端提交命令 → 服务器校验 → 规则结算
                                     ↓
                         更新本局状态与版本
                                     ↓
                         广播结果 → 三端显示
```

命令应携带本局标识、玩家身份、唯一命令编号、当前状态版本及动作参数。服务器还需要核对实际发送连接与该玩家身份匹配。一个命令不能通过改写角色编号获得另一只猫的行动权。

可靠有序传输用于需要顺序的操作和状态消息，但不能代替幂等检查。重复点击、客户端重发或重连后的旧请求仍可能出现；相同命令编号必须返回已处理结果或明确拒绝，不得再次修改状态。

状态保存已经发生的结果。界面可以重播文本和动画，但不能在播放结束时再次发放奖励。多人确认、战斗选择和技能选项使用唯一上下文标识；离开那个上下文后，旧按钮提交失效。

规则层未来可以按领域拆成月份、移动、成长、事件、战斗与救援模块，但每次拆分应由实际功能需要推动。状态修改和物品消耗尽量在同一次校验后的结算中完成，避免先扣物品、后发现剧情无效。

## 6. 未确定的设计如何进入开发

当前界面布局可以展示这些待定项的交互提案，M0 本地脚手架不依赖其裁定。进入相应功能实现前再集中确认，不新增故事解释。

| 待裁定内容 | 最晚需要明确的阶段 | 不明确会影响什么 |
|---|---|---|
| 下旬补给操作归属、结束条件及物资归属 | M1 | 多人补给与进入新月 |
| 当前猫暂停、受困时如何消耗行动 | M1 | 月份是否继续、状态能否解除 |
| 普通到格、0 步、传送、公交及回家额外行动的结束边界 | M1 / 接入对应地块前 | 重复触发与无限行动 |
| 共同剧情如何确认看完、是否逐页同步及跳过规则 | M2 / 共同观看完成衔接前 | 三端阅读进度与返回游戏流程 |
| 玩家掉线时如何处理本局等待、共同剧情与当前行动 | M2 | 网络中断时的可继续性 |
| 敌方行动次数、先后顺序、闪避提交与揭晓时点 | M3 | 战斗流程及难度 |
| 强制支援是否消耗同伴棋盘行动 | M3 | 战斗返回后轮到谁 |
| 普通全员复活的饱食数值、地点和原战斗去向 | M3 | 探索和普通战斗失败后的恢复 |
| 挂靠选择、携带两猫、承载者濒死后的转交 | M3 | 部分濒死的救援闭环 |
| 技能组合顺序、恢复 0.5 与归零先后 | M3 | 伤害、月耗和濒死判定 |
| 觉醒排程与濒死、受困的先后 | M3 | 自动觉醒是否延后、如何恢复 |
| 终战阈值、重试、额外闪避位的组合 | M3 | 救场和剧情只结算一次 |
| 结局后继续月份或重新进入战斗的范围 | M4 | 完整故事结束状态 |

开发遇到未决条件时，在策划文档登记问题、原稿位置和受影响流程。可以完成不依赖该问题的代码，但不能用猜测关闭该问题。用户确认后，先同步规则文档，再同步配置、实现和相关检查。

## 7. 检查、写作与提交规范

项目级执行细则见 `AGENTS.md`、`CONTRIBUTING.md` 和 `.agents/skills/our-home-workflow/SKILL.md`；本节说明每次工作的交付要求。

每个开发任务围绕一个能够验收的行为展开。实现之前说明依赖的规则和本次范围；完成后报告修改内容、执行过的检查及仍然缺失的能力。不要把“建立接口”写成“功能已完成”，也不要把“无界面通过”写成“联机已验证”。

文档区分三类内容：用户确认的玩法事实、技术实现决定、待确认设计。玩法调整更新策划文档；模块与阶段调整更新本技术文档；启动和检查方式更新开发说明。引用故事时写出截图页码或具体文件，不将技术设想回写成原稿事实。

建议提交信息采用 `类型(范围): 中文行为描述`，例如 `feat(scaffold): 建立三猫初始会话入口`、`fix(combat): 防止重发命令重复发放奖励`、`docs(rules): 记录普通复活裁定`。每个提交应只有一个清楚的变更目的，相关代码、配置、必要检查和说明一起提交。

提交前查看差异，检查是否混入 Godot 缓存、导出产物、机器绝对路径或原稿的意外改动。版本控制中保留需要的资源与稳定标识；忽略引擎生成的可重建缓存。文件使用 UTF-8，保持一致换行。是否创建提交、分支或推送，按用户本次授权及项目规范执行，不因建立规范就自动发布远端。

自动检查优先覆盖容易破坏规则的不变量：角色唯一性、顺序、饱食度精度、升级余量、一次性结算、状态转换和命令幂等。可复现随机输入用于检查不同结果路径；真实对局仍按既定技能和随机规则运行。低影响文案和布局调整用运行观察验证，不为每一句文本新增镜像测试。

每轮在[工作与决策记录](工作与决策记录.md)中登记助手决定、完成、未做、阻塞与依据。自测遵循[测试流程与用例规范](testing/测试流程与用例规范.md)，以[需求追踪矩阵](testing/需求追踪矩阵.md)关联用例、版本和实际证据。当前 M0 的 14 条用例与后续策划用例分开显示；未来需求未实现或未运行时不计入通过。快速检查用于日常回归，M0 验收还需真实 GUI 和视觉审阅；后续各阶段达到相应验收条件后才能标记完成。
